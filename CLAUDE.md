## 1. The product

- DeviceInfo ("Device Information" is the working name) for Android and Wear OS, as its own product with its own release lifecycle and root. The bootstrap snapshot of the goals: a phone app showing full device information (OS, hardware, SoC, display, storage, sensors, cameras, battery, network, diagnostics); a Wear OS app with glanceable tiles, hardware telemetry, sensors, battery status and Data Layer sync with the phone; advanced battery information carried from FastMediaSorter S4529 (charge speed, power profile, nominal profile, calculated time to charge, calculated runtime left). The completed upstream is the authority, not this list (section 2).
- Two installable packages from one repository: `phone/` and `wear/`. They share one application id and one Data Layer pair; the id is `com.sza.deviceinfo`, chosen 2026-11-13 and frozen from that day, when the Play Console app was created with it (section 3).
- Non-goals: media sorting, playback, cloud storage, SMB or SFTP sync. Coupling to FastMediaSorter: none - no shared code, no shared Gradle module, no shared release.
- Origin: `docs/BOOTSTRAP_HANDOFF.md`, written when FastMediaSorter S4528 created the repository boundary. It is a starting record; work is driven from the ticket store, not from the handoff.
- Read-only from sessions in this repository: `P:\ANDROID\FastMediaSorter_mob_v2` (the upstream source, modules `app_v2` and `wear`). `P:\ANDROID\StreamsPlayer_mob`, `P:\ANDROID\Tourist_mob` and `P:\ANDROID\filler_mob` are siblings of the same extraction pattern: reuse their decisions where they fit, never their code.

## 2. Standing law - upstream and parity

1. **The owner asked for the full functionality of FastMediaSorter's Device Information (System Info) sub-applications**, phone and wear, not a partial or redesigned substitute. Their checkout is never modified from here.
2. **Re-inventory before any parity claim.** The class list in the handoff (phone `ui/systeminfo/`, `core/systeminfo/`, `GatherSystemInfoUseCase`; wear `ui/apps/systeminfo/`, `domain/systeminfo/`, `data/wear/AndroidWearSystemInfo*`) is a starting list, not a baseline. Every port ticket (S0003 to S0006) first reads the upstream's actual code, resources and tests, and S4529's actual status for the battery work. Parity is claimed only against that fresh inventory. Since S0018 the inventory is mechanical: `docs/port-scope.json` states which part of the upstream is watched (System Info files, resources and help pages, string-key prefixes; exclusions carry a reason), and `tools/port-ledger/check-scope.ps1` fails on any in-scope file or string key that is neither ported nor decided in `docs/port-decisions.jsonl`.
3. **Port, do not rewrite.** A behaviour that can be ported with its tests is ported; a deliberate difference is recorded next to the code it concerns. The form of the parity inventory, decided in S0003's plan pass after the model of StreamsPlayer_mob and Tourist_mob: a committed port ledger, `docs/port-ledger.jsonl`, one row per ported file (upstream path and hash, destination path and dated hash, port date, optional carry date and pinned decision), and the drift check `tools/port-ledger/check-drift.ps1`, which re-hashes every upstream source and exits non-zero on an uncarried change. The destination hashes backfilled on 2026-11-14 are that day's baseline, not recovered port-time hashes. A ticket records each ported file with `tools/port-ledger/record-port.ps1` the moment the file exists; what it left out, and why, is the disposition table of its own record, which S0007 re-reads.
4. **No device claim without a device.** A phone or watch scenario that has not run on a device or an emulator stays an open manual check in its ticket (S0007), never a pass.
5. **Changes travel both ways.** The owner's decision in S0019 is that fixes and improvements travel between DeviceInfo and FastMediaSorter, each on its own ticket; FUNCTION-PARITY 0.1 rule 5 is the function-level carrier. Record a candidate first in `docs/reverse-port-notices.jsonl`, with its state, evidence and destination; the owner orders the FMS_A capture with `/sd fms-a: ...`. Only then record the FMS_A ticket id and hand-over state here. This repository's sessions never modify the upstream checkout. The initial local baseline and known differences are in `docs/reverse-port-baseline.md`.

## 4. Ticket store and the release package plan

- **The harness is adopted from the plugin, not copied.** Run any harness script through the forwarder: `pwsh -NoProfile -File tools/harness.ps1 <cluster>/<script> [args]` (for example `spec_catalog/validate`, `spec_catalog/select -Id S0002 -Format json`). Configuration is `.sza-profile.json` and nothing else; never edit or copy a harness script. The root launchers `r0.ps1`, `r1.ps1`-`r3.ps1`, `rs.ps1`, `rm.ps1`, `rw.ps1` are rendered by the harness scaffold; `a.ps1` is the project's own alias launcher over them and over the tools (section 6).
- **Ticket ids:** `S0001` onward (`^S\d{4}$`, the harness grammar). They overlap the id spaces of FastMediaSorter and the sibling products, so a ticket of another repository is always cited with the repository name next to its id.
- Specs: `PLAN/Sxxxx_<slug>.md`. Journal: `PLAN/spec-catalog.jsonl`, written only through `spec_catalog/insert`, `update`, `close`, `archive` - never by hand. Blockers are the literal `**Depends on:**` line or a `Blocker: Sxxxx` token; an id in prose is a mention, not a claim.
- **Scope of a behavior-changing ticket (S0021).** A ticket that changes user-visible behavior names its scope - phone, wear or both - and a one-sided change records why the other side does not get it, stated against the parity matrix `docs/PARITY_MATRIX.md`; the ticket updates the matrix rows it concerns in the same step, and the audit checks both the scope statement and the matrix rows.
- **Release package plan** - six decisions, recorded once:
  1. Files: `PLAN/RELEASE_QUEUE.md` (work remaining), `PLAN/RELEASE_READY.md` (ready), `PLAN/RELEASE_QUEUE_DONE.md` (shipped history, newest first).
  2. Single write path: every journal mutation goes through the harness's `Write-Catalog`, which calls `Sync-ReleaseQueue`; no skill or script maintains the files by itself.
  3. Ready set: `Implemented`, `Verified`, `BlockNeedUserTest`. Work remaining: `Draft`, `Approved`, `Tactical`, `In Progress`, `Partial`, `Broken`, `BlockByOtherTask`, `BlockQuestions`, `BlockExternal`. `Archived` leaves the plan.
  4. Package number: the `current-next-release:` marker in `PLAN/RELEASE_QUEUE.md`, starting at 1, advanced by `-Ship`. Not tied to a branch. `--` is the not-scheduled bucket.
  5. Operator commands (all through `tools/harness.ps1 spec_catalog/release-queue`): `-List`, `-List -Ready`, `-Validate`, `-Reconcile`, `-SetCurrent N`, `-Ship -Release N [-Version X] -DryRun`. Package headings and line order are the owner's; no script reorders them.
  6. `PLAN/` is **tracked**: an ignored ticket store would exist in exactly one place, and the tickets carry the owner's recorded decisions.

## 7. Code architecture

Read this before touching either module; each point needs several files to see.

- **Two apps, no shared source.** `phone` is View-based (ViewBinding, AppCompat and Material, a RecyclerView adapter); `wear` is Compose for Wear OS. They share an application id and a Data Layer pair but no Kotlin source set, so whatever both sides must agree on exists twice: `WearDataLayerPaths` (phone `service/`, wear `data/wear/`) and `WearSystemInfoReportPayload` (phone `domain/model/`, wear `data/wear/`, each with its own `WearSystemInfoReportCodecTest`). The phone test `WearDataLayerPathsParityTest` parses both path files and fails on any divergence; `WearSystemInfoReportPayloadParityTest` compares the report and acknowledgement declarations and format constant, and both codec suites read the frozen version 1 fixtures. Change the payload on both sides in the same edit and preserve mixed-version compatibility. Paths and acks: `/deviceinfo/watch/system_info_report` and `/deviceinfo/phone/system_info_report_ack` (`DATA-LAYER-PAIR`).
- **Phone report pipeline.** `GatherSystemInfoUseCase` builds the base sections in `buildSections()`, pulling field groups from the collectors in `core/systeminfo/` (`PlatformDetailsCollector`, `BatteryDetailsCollector`, `SensorsDiagnosticsCollector`, `MediaAudioDiagnosticsCollector`) and from `GatherCameraDiagnosticsUseCase`, then appends the sections of every `ExtendedDiagnosticsContributor` in a Hilt multibound set. That set is declared empty with `@Multibinds` in `di/ExtendedDiagnosticsModule`, so the public `store` flavor injects none; the `restricted` flavor (`phone/src/restricted`, owner decision of S0009: the seven noLegal sections live in a restricted build only) plugs in `RestrictedExtendedDiagnosticsContributor` with `@IntoSet` through `RestrictedExtendedDiagnosticsModule`. The flavor never ships: its release variant is disabled, it has no applicationId suffix and declares no permission, only a narrow `<queries>`; its tests are `src/testRestricted` (the contributor) and `src/testStore` (the public flavor carries none of it). The result is a `SystemInfoReport` with `sections`, `maskedText`, `fullText` and `hasSensitive`: fields flagged sensitive are masked in `maskedText` and shown only in `fullText`. Every source is read defensively (a failing one yields "unknown", a throwing contributor yields no extended sections), so the report is never partial by exception. `SystemInfoActivity` renders it through `SystemInfoAdapter`; sections are grouped by `SystemInfoGroup`, and a new collapsible group touches `SystemInfoGroup`, `SystemInfoGroupIcons`, a drawable and the section string (S0010 scope 1). Group expansion is persisted by `SystemInfoGroupStateRepository` over `CollapsibleSectionStore`.
- **Wear pipeline.** Each `*InfoContributor` in `domain/systeminfo/` implements `WearSystemInfoContributor` and is bound `@IntoSet` in `di/WearSystemInfoModule`; `GatherWearSystemInfoUseCase` sorts the set by `order` (a multibound `Set` has no iteration order, and a test asserts the order) and survives a throwing contributor. Hardware, health and environment reads sit behind the `data/wear/AndroidWear*DataSource` classes; `SystemInfoViewModel` feeds `SystemInfoScreen`. The report goes to the phone through `SendWearSystemInfoReportUseCase` and `AndroidWearSystemInfoReportSender`; on the phone `PhoneWearListenerService` hands it to `WearSystemInfoReportReceiver`.
- **Port conventions.** Upstream `src/main/java/com/sza/fastmediasorter/...` lands in `src/main/kotlin/com/sza/deviceinfo/...` (wear: `.../deviceinfo/wear/...`; upstream `src/noLegal/java` lands in `phone/src/restricted/kotlin`); the ledger rows in `docs/port-ledger.jsonl` show the mapping. Ported code relies on `-Xannotation-default-target=param-property`, set in both build files. A deliberate difference from upstream is written in the KDoc of the class it concerns (see `GatherSystemInfoUseCase`). Strings are ported by key selection: English base plus `values-ru` and `values-uk` in both modules (wear in `strings_systeminfo.xml`), and a string lands in all three in one edit.
- **Build logic and the release variant (S0008).** `buildSrc/.../buildlogic/` holds `VersionStamp` (PACKAGE-VERSIONING, Android profile: `PackageFamily.PHONE` band 0..5 in 10-minute slots, `WEAR` band 6..9 in 15-minute slots) and `ReleaseSigning` (reads the upload key from `keystore.properties`), both unit-tested in `buildSrc/src/test`. The root `build.gradle.kts` takes one clock reading per invocation into the root project's extra property `deviceinfo.buildInstant`; each module script then asks `VersionStamp.select`: a pin (`deviceinfo.pin.versionName` plus one code per family, together or not at all) wins, an invocation that names a release task stamps itself from the clock reading, anything else carries the sentinel of `gradle.properties`, which `select` checks against the formula. A release packaging task without the upload key stops in `gradle.taskGraph.whenReady` (`ReleaseSigning.isPackagingTask` matches the aggregate and the per-variant names, `bundleStoreRelease` included). `tools/release/VersionStamp.ps1` is the second implementation of the formula, and `check-version-parity.ps1` holds the two against the contract's vectors: change the formula in both in one edit. The Wear Data Layer payload classes are kept whole by `proguard-rules.pro` in each module (Gson reflects over them; the field names are the wire format).
- **Help (S0024).** One resolver, one map (CONTEXT-HELP rule 17). Phone: the Help action and F1 of `SystemInfoActivity` both call `HelpLauncher.open`, which reads `assets/help/help-map.json` (`HelpMap`, tree API of Gson so the release shrinker cannot rename what the map needs), asks `HelpResolver` (`none`, `inherit`, an element's anchor from the focused view's resource name, the top for the Help action itself) and starts `HelpActivity`, a WebView with JavaScript off over `assets/help/<locale>/<help id>.html` (`HelpPages`: the app's language when a page set exists, `en` otherwise). The pages are never edited: `tools/help/render-help.ps1` renders them from `tools/help/source/*.json` (en, ru and uk in one file per page; a control's name is a `nameRef` into the module's UI strings) into the app's assets and into `site/help/`, the same bytes. A new window or dialog needs a row in the map and a page source in the same edit, or `check-help-map.ps1` fails. Watch: no button and no key; `SystemInfoScreen` ends with a Help row (`WearHelpEntry`) and the phone page `watch-system-info` names the watch screen (CONTEXT-HELP 0.4 item L, reading A).
- **Ticket-tagged probes.** The `Timber.d("Sxxxx: ...")` lines (S0004 to S0007, S0024) are the status-bound debug probes of those tickets, and `.sza-profile.json` (`probes`) points the harness at `phone/src` and `wear/src`; do not delete or rename them by hand.
