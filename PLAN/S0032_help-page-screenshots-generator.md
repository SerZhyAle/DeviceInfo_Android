## 0. Owner request (verbatim)

Agent-noticed finding from S0024 (in-app help), not an owner order. CONTEXT-HELP 0.4 rule 8 item 3 and rule 14 ask every help page for a screenshot of the real surface with numbered markers, generated by a script from the real build, per locale and per theme, on demo content, with marker positions taken from the surface's own element bounds; rung 2 of section 4 asks the generator to regenerate every image and the marker bounds and fail on a difference. S0024 shipped the pages without the screenshot, because it needs a device or an emulator run: the pages are complete in text and the entries carry their numbered markers (phone/src/main/assets/help/<locale>/system-info.html and watch-system-info.html, rendered by tools/help/render-help.ps1 from tools/help/source/*.json). Wanted: a screenshot generator for the phone report window (and the watch screen) per locale en, ru, uk and per theme, on demo data; marker positions from the view hierarchy of the real build (the ids in the element rows of the help map give the views); the figure block and pins added to tools/help/render-help.ps1 per the reference template in the in-app-help catalog folder; the page footer then carries the product version the page was captured against (rule 8 item 7), which S0024 replaced with a revision date for lack of a capture; the rung 2 gate. Needs a device or emulator, so it is a release-tier or owner-run job, not a between-releases run.


## 1. Problem

The two help pages (the phone report window and the watch screen) explain a screen the reader cannot see: they have
numbered entries and no picture of the screen with the same numbers on it. A reader matches labels by sight, so the
page should show the real screen, in the reader's language and theme, with a numbered marker on every part the text
describes. The pictures must come from the real build, never be drawn or edited by hand, and the markers must come from
where the parts really are, so a layout change moves them. The footer of a page should say which product version the
page was captured against. And there must be a check that notices when a picture no longer matches the screen it shows.

### Assumed (unattended, 2026-11-14)

1. **Rung 2 is held in the static form** of CONTEXT-HELP 0.2 item D: every capture record stores a hash of what the
   screenshot could show (the layouts, menus, drawables, color, dimension and theme resources of the module, the base
   strings and the strings of the locale; for the watch, its Compose UI sources and resources; and the capture recipe
   itself) and `check-help-captures.ps1` fails a record older than any of them. Alternative weighed: regenerate every image on a device at each check and compare bytes.
   Rejected: it needs a device at every gate run, and emulator pixels move with the system image, so a byte gate would
   fail without a change in the product. A stale record is cleared by running the driver again. Cost accepted: a change
   to any string of the module's locale makes its record stale, including a string this screen never shows, because the
   hash cannot know which strings a screen reaches. Owner may overrule.
2. **Demo content is the clean state of a stock emulator image**, not a demo mode inside the app. The driver clears the
   app's data before each page, signs into nothing, and changes one thing on screen: it opens the first section so the
   rows and the section copy button are visible. Alternative weighed: a debug-only source of fixed demo values in the
   app. Rejected for this ticket: it is compiled source in the Hilt graph that this repository cannot compile between
   releases or run, and values of a stock image carry no author's or user's data (the sensitive fields are masked by the
   app). If a stricter reading of "demo content" is wanted, that is its own ticket. Owner may overrule.
3. **Language and theme are set through the platform, and checked in the capture itself.** The driver sets the
   per-app language with `cmd locale set-app-locales` (API 33 or newer) and the night mode with `cmd uimode night`.
   It then proves the capture: the title text in the UI dump must equal the locale's UI string (a screenshot in the
   wrong language is a defect, rule 14), and the average brightness of the image must match the theme asked for;
   a capture that fails either check is not written. Alternative weighed: set the system locale with root commands.
   Rejected: it needs a rootable image and a restart of the system UI. Owner may overrule.
4. **The watch has one theme**, so its record has one image and the page one picture without theme classes. The
   watch list is one scrolling column, so the picture shows its top; the Help row at the end of the list is recorded as
   absent (0.2 item C) and carried by the baseline, the phone's overflow entries likewise. Alternative weighed: a second
   scrolled shot of the watch. Rejected as a second image for one pin; the entry is complete in the text.
5. **Pins go where the part is, by one rule:** the pin sits at the vertical centre of the part's bounds, horizontally at
   its left edge plus half the pin or half the part's width, whichever is smaller (a toolbar button gets the pin on it,
   a full-width row gets it at the leading end). A part that occurs many times (a section row, a field row) is pinned
   at its first occurrence in view order. Pin positions are the same for both themes because the layout is: the driver
   compares the two and refuses a capture whose positions differ by more than half a percent.
6. **Images are scaled to at most 540 px of width** by the driver and committed as PNG under `tools/help/captures/`;
   the generator copies them to the app's assets and to the site as the same bytes (rule 12: the page makes no
   request). Alternative weighed: full resolution. Rejected: about 12 images in two places at 150 to 300 kB each.
7. **The footer version is the version name of the installed package, never the build sentinel.** A debug build carries
   the non-releasable sentinel of `gradle.properties`; the driver refuses to record it and asks for `-ProductVersion`
   (the version name the release pin prints). Alternative weighed: record the sentinel. Rejected: it would publish a
   version that never existed. The capture is therefore part of the release run, after the pin is printed.
